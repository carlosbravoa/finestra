# wdcomp

A headless Wayland compositor. Real applications connect to it, and it takes
the pixels they render.

It has two sinks. With `--ipc` it streams damaged rectangles, deflated, to the
node server over **fd 3** — that is how they reach a canvas in the browser, and
it is how the server runs it. Without `--ipc` every commit is written to a PNG,
which needs no browser and no server and is how this is debugged.

Pointer and keyboard input come back the other way. See
[`../docs/wayland.md`](../docs/wayland.md).

## Building

```bash
make            # -> build/wdcomp
make check      # is everything installed?
```

Needs `libwayland-dev`, `libxkbcommon-dev` and `zlib1g-dev` — and nothing else.
The protocol marshalling is generated by `wayland-scanner` from the XML in
[`protocols/`](protocols/), so none of it is hand-written. Those files are in
the repository rather than read from `/usr/share/wayland-protocols`, because
which of them a distribution ships depends on its release date and not on the
protocol; `protocols/README.md` has the table. A C compiler is already a
requirement of this project via `node-pty`.

The build is optional. When `wdcomp` is absent the desktop simply has no
Wayland app, the same way a disabled app is absent.

## Running

```bash
./build/wdcomp -n 1 -- gnome-calculator
```

That starts a compositor on `WAYLAND_DISPLAY=wayland-wd`, launches the
application against it, writes one frame to `/tmp/wdcomp/frame-000.png` and
exits. Without `--`, it waits and prints the socket name so you can point a
client at it yourself.

```
  -s, --socket NAME   wayland socket name (default wayland-wd)
  -g, --size WxH      size to configure windows at (default 800x600)
  -o, --out DIR       where to write frames (default /tmp/wdcomp)
  -n, --frames N      exit after N frames
  -i, --ipc           stream frames over fd 3 instead of writing PNGs
  -l, --layout NAME   xkb keyboard layout (default us)
      --variant NAME  xkb layout variant
      --no-force-shm  do not push the client's toolkit off the GPU
  -v, --verbose       log damage rectangles and protocol detail
```

`./smoke.sh` does a build-and-render check against whichever GTK application it
can find, without involving the server.

`tests/wayland.mjs` covers the other half — the service, the frame wire format
and process reaping — and runs as part of `npm test`. It skips itself when the
compositor is not built or the host has no desktop application to run, so it
stays green on a bare server.

Why fd 3 and not stdout: the application inherits stdout, and under
`dbus-run-session` so does the bus daemon. One stray line of theirs would shred
the frame stream.

## Two things that will waste your afternoon

**Applications need their own session bus.** A `GApplication` that cannot
register on a session D-Bus exits with status 0, no window and no error
message. And if it registers on your *own* bus while that application is
already running in your real desktop session, the single-instance protocol
hands the window to that instance — it opens on your physical screen and
`wdcomp` sees nothing. Run it under `dbus-run-session` when the application is
a GNOME one:

```bash
dbus-run-session -- ./build/wdcomp -n 1 -- gnome-text-editor /tmp/notes.txt
```

**GPU applications produce buffers this stage cannot read.** GTK 4 and Qt Quick
render on the GPU and submit dmabuf handles, which need an EGL import that
stage 1 does not do. `--force-shm` is on by default and sets
`GSK_RENDERER=cairo`, `QT_QUICK_BACKEND=software` and `LIBGL_ALWAYS_SOFTWARE=1`
in the client's environment, which is enough for GTK 4. If you turn it off and
see *"commit with a non-shm buffer"*, that is what happened.

## What is implemented

`wl_compositor`, `wl_shm` (by libwayland), `wl_output`, `wl_seat` with a
pointer and an xkb keyboard, `wl_subcompositor` and `wl_data_device_manager`
as stubs, and `xdg_wm_base` with both the toplevel and popup roles.

Keys travel as evdev codes, not characters: the keymap goes to the client as a
file descriptor and it translates for itself. Modifier state is derived here
from an `xkb_state` rather than trusted from the browser, and losing focus
releases everything still held.

Window identity lives on the `xdg_surface`, not the toplevel, which is what
lets a menu be streamed, positioned and clicked through exactly the same path
as the window it belongs to.

Damage rectangles are tracked and logged under `-v` even though stage 1 writes
whole frames — they are what goes on the wire in stage 2, so they are worth
watching now.

Only the first toplevel of a session is streamed. Dialogs and secondary
windows are announced and then ignored, because each needs its own shell
window — that is stage 4.

Menus, tooltips and dialogs all arrive as their own windows, placed by the
real `xdg_positioner` rules and constrained to the parent window. A menu that
holds a grab takes the keyboard, so Escape closes it, and a click outside
dismisses it.

Cursor shapes come from `wp_cursor_shape_v1`, and the clipboard from a real
`wl_data_device` — copying out of an application works; pasting in has a
toolkit-side limitation described in `docs/wayland.md`.

Not implemented: `xdg-decoration` so Qt applications can use the shell's own
frame, dmabuf and subsurface composition (6).
